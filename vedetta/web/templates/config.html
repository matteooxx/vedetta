Write this file with your own AI

An assistant that has read your CV can fill most of this in a minute, and the hard part was never the YAML — it is knowing what the keys mean. The prompt below carries the whole schema with it, so the assistant has the exact key names rather than a guess at them, and it is generated from the file on disk, so it cannot describe keys this program does not read.

  1. Copy the prompt below. Open it as plain text if that is easier to select whole.
  2. Paste it into whichever assistant you use, and attach your CV. It is told to ask you about anything your CV does not say rather than invent it, so expect questions, and answer them.
  3. Paste what it gives you into the box above and press Check, without saving. You will see what it would do to the postings already here before anything is written.
  4. Save when the numbers look right. A timestamped backup is kept beside the file, so a bad answer is undone by putting the old one back.
It is told not to guess. A configuration file full of confident filler is worse than an empty one, because you would believe it. The prompt's first rule is to collect every gap into one list of questions and wait, and to leave a key out rather than fill it in — an absent key means "no opinion", which this program handles.

Why there is no prompt for this file

An assistant asked for a company's hiring-platform identifier will produce one that looks right. During this project's design two independent automated sources each returned a different company than the one asked for — one of them a road-paving contractor returned as an asset manager, and a vendor's demo board returned as Amazon's, complete with a posting called "GCO Test Position".

So a source is only ever polled once a human has looked at real postings from it and written the date into verified_on. An assistant can still help with the easy half: ask it for employers worth watching and their careers page, then find each one's real feed yourself and confirm it.

What this file controls

{% if name == 'profile' %}

What you can actually take on: languages, work authorisation, level, and geography. It is what decides whether a posting is workable.

  • locations — four buckets. A posting usually lists several locations and the best verdict wins, because one workable office makes the posting workable. An unrecognised location is never excluded; it is shown and labelled unclear.
  • experience.reject_level — matched word by word against the title, and tested before accept_level. The other order read “Associate Renewals Manager” as junior.
  • tracks.require_match — the most effective setting here and the most likely to be wrong. It needs your cluster rules to be broad enough; check the excluded list for a week before trusting it.
  • exclude_if — only the rule ids you list make a posting unworkable. Anything else stays a warning you can see and overrule.

Nothing is ever deleted. An excluded posting is counted, explained and one click away.

{% elif name == 'watchlist' %}

Which employers to watch, on which platforms, with which identifiers. A source is polled only when it carries verified_on. Remove that line and the source stops being polled while staying visible as unwatched — which is the point: an employer you cannot watch should never look like an employer with nothing to say.

{% elif name == 'rules' %}

What counts as a blocker, a warning or a good sign. Three keys matter most:

  • unless — the difference between a language that is required and one that is an asset. Without it a language rule is wrong about half the time.
  • field: title | body | all — what the rule reads. The first real run labelled a “Senior Backend Engineer” as early career, because the word “graduate” sits in nearly every long description’s boilerplate.
  • weight — so that being in a target role cluster outweighs merely being at the right level.

explain is required on every rule, because it is what appears next to the posting. A rule you cannot explain in one line is a rule you cannot argue with.

{% else %}

Database path, digest time and recipients, ranking weights, and which discovery techniques are enabled. Credentials are never here — they come from the environment file only.
